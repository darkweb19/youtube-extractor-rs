# On-demand GCP extraction worker (Ubuntu 24.04)

For the complete Railway → Cloud Run controller → Compute Engine architecture,
see [architecture](../docs/architecture.md). For the setup sequence, independent
Tunnel/Access ingress and WARP egress checks, credential boundaries and recovery,
see [GCP/Cloudflare operations](../docs/gcp-cloudflare-operations.md).

This directory is the **GCP deployment unit**. It packages the existing Rust/Axum
service as a binary instead of maintaining a fork of its request parsing,
job queue, cancellation, or file streaming code. GCP receives only the generated
`gcp-worker/bundle/` folder; Railway keeps the UI and public API.

## Manual recovery via prebuilt ZIP (automated deployment preferred)

The preferred process is now **automatic**: a reviewed push to `main`
creates a private Cloud Storage release, and the worker installs it on its
**next VM boot**, with no binary download, browser SSH upload or manual service
restart. See the [automated GCP deployment guide](../docs/automated-gcp-deployment.md)
for one-time IAM/instance metadata configuration, verification and rollback.
Existing worker environment and Tunnel settings are preserved.

The ZIP below is retained as a **manual recovery path**. GitHub Actions
compiles and packages the worker for **Ubuntu 24.04 amd64**. You do not need
Git, Docker, `cargo`, or `gcloud` on your computer or the VM.

1. Open [Actions](https://github.com/darkweb19/youtube-extractor-rs/actions/workflows/gcp-artifact.yml)
   on the intended branch/commit. Open a successful
   **GCP Worker - Build and Deploy** run; builds run on selected main or feature branch pushes.
2. Under **Artifacts**, download `gcp-worker-ubuntu24-amd64`.
   Your browser downloads `gcp-worker-ubuntu24-amd64.zip`.
3. In Google Cloud Console > Compute Engine > VM instances, click **SSH** for
   your Ubuntu 24.04 instance. Use the SSH-in-browser **Upload file** button
   to upload that ZIP into your home directory.
4. Run these commands **on the VM** (no Git or Docker):

```bash
mkdir -p "$HOME/extractor-bundle"
unzip -o "$HOME/gcp-worker-ubuntu24-amd64.zip" -d "$HOME/extractor-bundle"
cd "$HOME/extractor-bundle"
sha256sum -c SHA256SUMS
bash setup-ubuntu.sh
```

The setup script installs runtime dependencies (system-wide Deno, FFmpeg,
Python and yt-dlp). WARP is optional and not required for the worker.
It does not install Git, Docker or Rust.

5. Leave existing WARP registration untouched if installed. For the current
   working download path, configure yt-dlp for **direct GCP egress** and verify
   that `sudo -u extractor /usr/local/bin/deno --version` succeeds after the
   `install-service.sh` step.
6. Configure Cloudflare Tunnel + Access and Railway secrets as documented
   below before enabling `EXTRACTOR_MODE=remote`.

The artifact ZIP is generated by GitHub, not by this VM. Artifacts expire
after 14 days. Every new feature-branch push generates a fresh artifact.

## Optional developer packaging (requires Docker on build computer only)

On a Docker-capable workstation (builds a Linux/amd64 Rust 1.99 binary):

```bash
bash gcp-worker/package.sh
gcloud compute scp --recurse gcp-worker/bundle INSTANCE_NAME:~/extractor-bundle --zone ZONE
```

On your Ubuntu 24.04 VM:

```bash
cd ~/extractor-bundle
bash setup-ubuntu.sh
# Direct GCP outbound networking worked in the November 4 diagnostic test.
# WARP is NOT needed for metadata or download requests.
/usr/local/bin/deno --version
sudo install -m 0600 worker.env.example /etc/youtube-extractor.env
sudoedit /etc/youtube-extractor.env   # SET API_TOKEN to a unique secret first
bash install-service.sh
curl -fsS http://127.0.0.1:8080/health
```

**Security**: worker listens only on localhost. Do not expose port 8080 or
SOCKS port 40000 in VPC firewall rules. Install **cloudflared** and set up a
named Cloudflare Tunnel for `http://127.0.0.1:8080` using a stable hostname;
protect the hostname with Cloudflare Access service-token policy. Use a
Cloudflare-managed tunnel token installed via `sudo cloudflared service install`
and verify it reconnects after VM boot. Never check tunnel tokens into Git.
Railway requires `GCP_WORKER_URL` pointing at that HTTPS hostname plus its
Access client ID/secret and worker bearer token. The VM needs outbound access to YouTube and for Cloudflare Tunnel.
Cloudflare Tunnel/Access protects the worker's inbound API separately from WARP.

A bare TCP port or unprotected tunnel is **not** an acceptable production setup.
Verify `systemctl is-enabled youtube-extractor cloudflared`; WARP is optional.

## VM startup and shutdown

Railway's `EXTRACTOR_MODE=remote` starts the VM through the keyless Cloud Run controller,
waits for RUNNING + `/health`, then submits jobs to the worker's existing
bounded Tokio queue. Queued jobs use UUIDs. Railway transfers outputs to its
own storage before declaring success. Railway stops the VM after 300 seconds
without active operations **only for a VM it started**. A manually started VM remains running for troubleshooting.
After a controller `POST /start` returns `202` (a new start), Railway records
the worker's Linux boot ID in `DATA_DIR/.railway-vm-ownership` (persistent volume
required). On a Railway process restart, the idle watcher validates that the live worker still
has that boot ID before issuing `POST /stop`. A VM manually rebooted after the
original Railway start has a different boot ID and is never stopped using a
stale ownership marker. If ownership cannot be verified or the worker activity
check fails, shutdown fails closed. Use the independent GCP maximum runtime
as a cost guard for these cases. If a new request arrives during a stop, it must
wait and restart the same VM (never duplicate instances).

The idle interval defaults to `GCP_IDLE_TIMEOUT_SECS=300` and is checked every
15 seconds after active Railway operations finish. Worker jobs and in-flight
file transfers also block shutdown. Retained completed files do not keep the VM
running; Railway serves its own copy.

A `200` response to `POST /start` means the VM was already running and does not
grant Railway ownership. The controller must return `202` only when it actually
initiates the start, so a concurrent manual start cannot become Railway-owned.
A successful `POST /stop` means the request was accepted, not that the VM has
stopped. Railway retains the boot-bound ownership record, checks subsequent VM
state and retries while that same boot remains running. Ownership is cleared
when the VM reaches `TERMINATED` or a different worker boot is observed. Missing
boot identity, failed activity checks and unknown activity block shutdown safely.

If the VM stays running beyond the idle interval, check Railway logs for
`idle_shutdown_requested`, `controller_request_rejected`, `worker_activity_failed`,
and `Idle VM stop attempt failed`. Enable
`RUST_LOG=info,youtube_extractor::remote=debug` to see `idle_shutdown_skipped`
reasons. Confirm the controller supports stop with its VM identity/IAM, the worker
provides `boot_id` on health and activity replies, and `DATA_DIR` is persistent.
Deploy the current worker binary if those fields are missing; do not fabricate
ownership for an already running VM. Start a new verification cycle with the VM
stopped, then submit a job through Railway.

**Configure an independent GCP maximum VM run duration** with termination
action STOP, e.g.:

```bash
gcloud compute instances stop INSTANCE_NAME --zone ZONE
gcloud compute instances set-scheduling INSTANCE_NAME --zone ZONE --max-run-duration=1h --instance-termination-action=STOP
```

This is a hard cost guard; it can interrupt long jobs. Leave the VM stopped
after setup, then submit through Railway. Persist Railway DATA_DIR on a
Railway volume and run a **single Railway replica**. The in-process queue is
not a multi-replica database queue and in-flight downloads are not transparently
resumable after a crash. Job retry policy must be bounded.

## Troubleshooting

```bash
sudo journalctl -u youtube-extractor -n 100 --no-pager
warp-cli status
curl --proxy socks5h://127.0.0.1:40000 https://www.cloudflare.com/cdn-cgi/trace | grep warp=
curl -fsS http://127.0.0.1:8080/health
```

WARP behavior can change, and the network path is not guaranteed to stay usable
for all videos. Download only media you are permitted to retrieve.

### Controller lifecycle failures

The old `VM controller rejected lifecycle request` message proves that a
controller `POST /start` or `POST /stop` returned a status other than `200`,
`202` or `409`. During download startup, `/start` is the likely operation.
That message alone cannot establish why it failed. Updated job errors include
the controller method/path and status, for example `VM controller POST /start
returned HTTP 403`, followed by a fixed troubleshooting hint.

| Controller HTTP status | Check |
| --- | --- |
| `401` | Railway's `GCP_CONTROLLER_TOKEN` matches the controller secret |
| `403` | Cloud Run invocation policy and controller token validation; if the request reaches the application, its attached runtime identity's VM permissions |
| `404` | Controller HTTPS origin/routes and its configured VM project, zone and instance |
| `405` | Controller implements the required HTTP method for that route |
| `3xx` | Redirects are intentionally blocked; configure the final HTTPS controller origin directly |
| `429` | Controller rate limits or upstream quota; retry after the limit clears |
| `5xx` | Cloud Run service logs, runtime identity/IAM and VM target configuration |

Redeploy Railway from the pushed `fix/rust-yt-bot` commit before collecting the
new diagnostics. In browser DevTools **Console**, enable **Preserve log**,
filter for `[Frame]`, include the **Verbose** level for debug polling, and
reproduce once. A poll may return HTTP `200` while its JSON job status is
`failed`; inspect the displayed job error for the separate upstream controller
status.

Use the safe `job_id` to correlate browser events with Railway JSON logs from
`youtube_extractor::remote`. The `remote_job` span contains `job_id`; controller
events record `operation`, `method`, `path`, `http_status` and `elapsed_ms`.
Transport failures instead report a safe `error_category`. `RUST_LOG=info`
shows lifecycle stages. Set `RUST_LOG=info,youtube_extractor::remote=debug` if
idle-skip reasons are also needed. Metadata operations use the
`remote_metadata` span.

Match the method, path, status and time with **Cloud Run request logs**, then
inspect the controller's **service logs** to distinguish an invocation-policy
rejection from controller token validation or VM IAM failure. If `GET /status`
works but `POST /start` fails, inspect POST route handling and VM start
permissions first; Cloud Run IAM generally gates every request, but that
observation alone is not conclusive. Never log or paste tokens, raw headers,
controller response bodies or video URLs when collecting diagnostics.

## Deploying the worker response contract fix

`POST /api/v1/downloads` returns HTTP `202` with the same `JobView` JSON model
used by `GET /api/v1/downloads/{id}`. Its `progress` contains
`downloaded_bytes`, nullable `total_bytes`, and nullable `percent`; it does not
contain the internal pipeline's `stage` field. Railway now decodes the shared
model and derives its internal stage from the validated job state (`queued`,
`running`, `completed`, `failed`, or `cancelled`). Both replies must contain the
expected UUID, and malformed JSON, invalid field types, and unknown states fail
validation. Railway copies byte counts directly, even when the total is unknown.

1. Wait for the branch validation, GCP integration tests, and prebuilt worker
   workflows to succeed for the intended `fix/rust-yt-bot` commit. In Railway,
   select that branch/commit and deploy or redeploy the existing service using
   its Dockerfile. Keep its persistent `/data` volume and one replica.
2. Keep the existing remote-mode controller, worker, and Cloudflare Access
   variables. No new variable, secret, Cloud Run controller deployment, VM
   scheduling change, or tunnel change is required for this fix.
3. An existing worker that returns the documented `JobView` contract does **not**
   need redeployment: the fix is in Railway's response consumer. If refreshing
   the worker independently, use the successful commit's prebuilt ZIP and the
   installation procedure above; retain `/etc/youtube-extractor.env` and its
   existing credentials.
4. Verify Railway `/health`, then submit one download of media you are permitted
   to retrieve. Confirm `worker_dispatch_response` reports `202`, followed by
   `worker_dispatch_accepted`, expected state transitions, a completed local job,
   and a file that can be retrieved and probed. Confirm the VM stops after the
   configured idle interval. Also verify cancellation against a running job.

An HTTP `200` in browser job-status polling only confirms that Railway served
the poll. Inspect the returned job state and Railway's correlated `remote_job`
logs to establish the worker's result. Contract failures use
`worker_dispatch_invalid` or `worker_job_poll_invalid` with a fixed reason such
as `invalid_response_body`, `invalid_uuid`, or `job_id_mismatch`. Logs include safe
status/category metadata and the expected job ID; they exclude raw bodies,
worker error text, private URLs, and credentials.

The regression suite uses local HTTP worker fixtures serialized from `JobView`.
It does not establish live Railway/GCP/Cloudflare or YouTube download success;
the deployment checks above must run in the selected deployment to establish
that. Roll back through Railway's deployment history if required, retaining the
volume and configuration; the older consumer will still have the contract bug.

## Apply direct egress on an existing GCP VM

Updating the source/example environment file **does not change** the existing
`/etc/youtube-extractor.env`. After installing the new prebuilt worker bundle,
back up and update that file, keeping its current API token:

```bash
sudo cp -a /etc/youtube-extractor.env /etc/youtube-extractor.env.backup
sudo sed -i -e '/^YTDLP_PROXY=/d' \\
  -e 's/^YTDLP_PROXY_REQUIRED=.*/YTDLP_PROXY_REQUIRED=false/' \\
  /etc/youtube-extractor.env
printf '%s\\n' 'YTDLP_JS_RUNTIME=deno' | sudo tee -a /etc/youtube-extractor.env >/dev/null
sudo systemctl daemon-reload
sudo systemctl restart youtube-extractor
sudo -u extractor /usr/local/bin/deno --version
curl -fsS http://127.0.0.1:8080/health
```

Do not append a second `YTDLP_JS_RUNTIME` setting if one already exists;
update the existing line instead. Existing Cloudflare Tunnel/Access credentials
and `API_TOKEN` do not change. To diagnose the next failure:

```bash
sudo journalctl -u youtube-extractor --since '15 minutes ago' --no-pager -o cat
railway logs --service YOUR_RAILWAY_SERVICE --environment production --since 1h --lines 500
railway logs --service YOUR_RAILWAY_SERVICE --environment production --since 1h --lines 500 --filter 'idle_shutdown_requested OR worker_job_failed OR vm_ownership_saved'
```

`RUST_LOG=info,youtube_extractor::remote=debug` on Railway exposes idle-skip
reasons; avoid outputting credentials or raw YouTube playback URLs.

## Railway controller configuration

Provision a separate Google Cloud Run VM controller implementing the contract
below. Bind the project, zone and instance in the controller's configuration;
Railway cannot select an arbitrary VM. Attach a runtime service account to Cloud
Run with narrowly scoped permissions to inspect, start and stop only that VM:
`compute.instances.get`, `compute.instances.start` and `compute.instances.stop`.
The controller uses its attached runtime service identity for keyless Google
authentication. Railway never calls Google OAuth or Compute Engine directly.

Store the same independently generated controller secret in the controller's
secret configuration and Railway's `GCP_CONTROLLER_TOKEN`. Use at least 32
visible ASCII characters, for example a secret generated with `openssl rand
-hex 32`. Keep it separate from the worker's bearer token and Cloudflare Access
service token. Neither application logs nor error responses should contain it.
Configure the controller's ingress and Cloud Run invocation policy to permit
Railway's requests: Railway supplies the application-level `X-Controller-Token`
header, not a Google IAM identity token. The controller must authenticate that
header before inspecting or changing the VM, reject missing/incorrect tokens,
and avoid exposing unauthenticated lifecycle operations. Cloudflare Access
service tokens remain authorized for the worker's hostname.

`GCP_CONTROLLER_URL` must be an HTTPS origin, with no embedded credentials,
non-root path, query or fragment. Each request carries `X-Controller-Token`:

| Method and path | Controller response |
| --- | --- |
| `GET /status` | HTTP `200` with JSON `{"status":"RUNNING"}` or another Compute Engine state |
| `POST /start` | HTTP `202` when start is accepted, `200` if already running, `409` during a transient lifecycle state |
| `POST /stop` | HTTP `202` when stop is accepted, `200` if already stopped, `409` during a transient lifecycle state |

Lifecycle requests do not need a JSON response body. `202` indicates acceptance;
Railway still polls VM state and worker readiness before dispatching work.
`409` causes later polling/retry within the existing startup/idle lifecycle.
Controller calls have bounded connection/request timeouts and never follow
redirects. Unexpected HTTP codes, malformed state replies and unavailable
controllers return safe errors without logging tokens or controller bodies.
Worker requests retain their separate bearer and Cloudflare Access headers.

The controller must be deployed separately; this worker bundle does not deploy
or configure Cloud Run. For migration, remove `GCP_SERVICE_ACCOUNT_JSON` and the
old project/zone/instance variables from Railway, configure the two controller
variables, verify lifecycle operations, then revoke/delete the former
service-account private key in Google Cloud. Do not retain it as a fallback.

```dotenv
EXTRACTOR_MODE=remote
GCP_CONTROLLER_URL=https://controller.example.run.app
GCP_CONTROLLER_TOKEN=<separate random secret of at least 32 visible ASCII characters>
GCP_WORKER_URL=https://worker.example.com
GCP_WORKER_TOKEN=<same random token as worker API_TOKEN>
CF_ACCESS_CLIENT_ID=<access service token client ID>
CF_ACCESS_CLIENT_SECRET=<access service token secret>
GCP_IDLE_TIMEOUT_SECS=300
GCP_START_TIMEOUT_SECS=300
GCP_MAX_JOB_ATTEMPTS=2
# To forward 5 jobs and let GCP execute 2 at once:
WORKERS=5
QUEUE_CAPACITY=16
DOWNLOAD_TIMEOUT_SECS=3600
```

Run a single Railway replica with persistent `DATA_DIR`. GCP worker uses
`WORKERS=2`. Only GCP makes YouTube requests; Railway receives a completed
file and can perform further local FFmpeg processing. The current yt-dlp worker
can also use FFmpeg locally to merge YouTube's separate audio/video streams,
so FFmpeg is installed in both environments.

### Failure/restart limits

Queued Railway jobs are replayed from persistent job records after a restart;
running jobs are marked interrupted rather than silently double-dispatched.
Use the Google Cloud maximum-VM-runtime scheduling policy as the independent
runaway-cost guard. The code uses a single-process lifecycle lock and therefore
is **not** safe for multiple independent Railway replicas; a multi-replica
deployment requires a distributed lease and durable dispatch attempts.
Transient HTTP dispatch transport failures are retried once with the same
idempotency key. Worker `failed` states now preserve their typed `JobError.code` on Railway.
`ACCESS_RESTRICTED` and `UPSTREAM_RATE_LIMITED` are not blindly retried;
only `DOWNLOAD_INTERRUPTED` may trigger a fresh extraction attempt up to
`GCP_MAX_JOB_ATTEMPTS` (two by default). Missing worker error details still
fall back to `DOWNLOAD_INTERRUPTED`. Worker-side yt-dlp stderr is buffered
briefly and classified into **fixed safe diagnostics**; signed media URLs,
cookies and raw stderr are never emitted to Railway or the frontend.
